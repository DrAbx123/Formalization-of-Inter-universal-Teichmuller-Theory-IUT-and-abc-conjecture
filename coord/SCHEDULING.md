# SHEAF 项目级调度：大规模分组并行

2026-10-22。**项目不设固定 agent 总数、组数或每组人数上限。** 并行规模可以达到数百个执行者；实际启动多少，由目标相关的就绪任务、依赖冲突、文件权属、审查/集成吞吐及真实资源决定。这里的规模是方法支持的组织方式，不是当前工具已通过数百并发实测的声明。

**本次 chat 的单线程要求只约束本次方法论文档编辑。** 它不是项目设置，不限制后续证明工作的 agent 数，也不要求后续所有任务经 root 逐个派发。本页修改方法，不授权本次编辑自行启动证明团队。

## 1. 采用 SHEAF 的角色分工，不把 root 变成派发瓶颈

| 角色 | 职责 | 无需承担的工作 |
|---|---|---|
| 总协调 / launcher | 固定目标、阶段策略、分组边界、资源优先级和重大接口冲突 | 逐个启动所有 worker、逐行审批、复读所有源码 |
| 维护者 / maintainer | 维护全局 DAG/就绪队列和集成记录，统一构建、发布验证产物、处理公共修复 | 代替各组证明数学、让全项目等待一个叶子 |
| 组负责人 / lead | 认领一组相关任务，向组内执行者提供完整上下文，审查、集成并追踪构建结果 | 仅转发消息的空主管层 |
| 执行者 / worker | 完成当前节点/模块，交付后从可领取队列继续相邻任务，保持数学上下文 | 每换一个相关节点都等待 root 重新写提示词 |

分组按证明主题、稳定接口和可变文件边界形成；组数随任务图变化。小任务中角色可以合并，大规模时可由多个组负责人分担审查与集成。没有固定五层树，也不强制把所有执行者扁平挂到 root。

总协调授权组的完整问题范围后，组内分派、正常证明修复和领取后续任务由组内自主完成。改变最终目标、跨组文件权属或公共接口约定才进入相应协调；不恢复旧多级 SQLite 逐项审批。

## 2. 就绪队列决定扩展到多大

全局队列来自目标相关 DAG 与目标 import 闭包，遵守各阶段顺序：

- 阶段 1：从目标向下，给出实际对象、来源和证明分解；关系不明的只开展有界调查。
- 阶段 2：该节点自然语言证明已明确，statement dependencies 已准确声明，才可写 Lean 陈述。
- 阶段 3：目标已锁定，proof dependencies 已准确声明，即可尝试证明；依赖不必全部证完，上层与下层可以并行，传递缺口必须保留。

维护者刷新就绪/等待状态，组负责人和 worker 原子认领可领取项目。worker 交付后优先领取与刚完成节点相邻、属于本组范围的就绪任务；没有相关工作再取队首。这样扩大并行时复用已有数学上下文，不让 root 不断重发背景。

认领必须检查目标、文件和版本，不能只抢一个任务名称。共同前置只认领一次；依赖它的所有消费者指向同一节点。未就绪任务不能因为有空闲 agent 就发出去猜接口。

有更多互不冲突的就绪包，且执行、审查、构建资源可承担，就增加执行者或工作组。没有独立工作时减少活动执行者；不按预设人数填满队列，也不人为封顶。工具当次拒绝或资源耗尽只代表当次可用容量，不把旧名额数写成永久限制。

## 3. 如何让很多执行者互不干扰

| 冲突类型 | 处理方式 |
|---|---|
| 同一生产文件需要多个修改 | 一个文件 owner 负责集成；任务合包或串行，不能多个 worker 直接覆盖 |
| 同一缺失定理被多处需要 | 一份节点、一份认领、一份供体证明；消费者共享准确类型及版本 |
| 共同定义/实例尚不稳定 | 由该接口 owner 提交统一变更集，相关消费者同步适配；不各造新定义 |
| 同一任务的过期实例还在运行 | 先确认停止，再交接认领和可变文件；不能因租约到期让两实例双写 |
| 文件互不重叠、输入已冻结 | 可同时执行；不要求数学主题完全不同 |
| 证明依赖已有准确陈述但仍待证 | 按 SHEAF 并行工作，结果标为未闭合；不倒退成所有前置先证完 |
| 原目标之外的漂亮定理 | 不进入活动队列，人数多不构成新增无关工作理由 |

每包给出精确可修改文件。公共规则和冻结接口可共享读取；源码在交付并停止写入后供评审，或评审已登记的不可变快照。审查者不读一份正在变化的文件后宣称验收另一个版本。

组/任务使用独立 sandbox、日志和试验产物，数学成果经审查进入同一生产库。sandbox 不是复制理论、隐藏额外假设或绕过文件权属的渠道；重用同一 Mathlib 和既有接口。

Windows 路径认领要归一化，避免大小写、相对路径或链接把同一文件伪装成不同文件。认领和落位是短时原子操作，数学证明不占全局锁。

## 4. 分组落位与统一构建

执行者在自己的试验范围做单文件检查，组负责人审查命题强度、依赖、缺口和重复声明，合格后落位。修改公共定义/实例的内容与受影响消费者作为一个变更集处理，保存可恢复的前一版本。

生产库只有一个受协调的集成/发布序列。全局构建在稳定源码快照中进行，各组继续对自己的任务工作；绿色产物再发布，失败快照不污染大家正在使用的编译产物。落位记录区分“已进入源码”和“已经过全局构建验证”。

维护者统一管理共享编译产物；同一输出目录不能多进程竞争写入。真正隔离产物且 CPU/内存允许的局部编译可并行。数百个数学执行者不意味着数百份同时写同一 `.olean` 的构建。

审查或构建积压时，先扩展独立审查能力、合并相关变更、分批构建或暂停相关写入，保持不依赖它们的研究任务继续；不要因共享发布串行就把所有数学任务串行化。新增维护角色须承担实际工作，不制造常驻观察者。

## 5. 由事件恢复，持续剪枝

交付、接口版本更新、构建结束、原子认领释放或资源恢复触发队列刷新。执行者等待明确接口时保存检查点并结束本次执行；有结果再恢复。一个叶子等待只阻塞相应后继，其他组继续领取独立工作。

证明走通后删除无用 imports、更新实际 proof edges，并把不再从目标可达的任务移出活动队列。正在进行的废弃分支停止并保留成果，不因已经派了很多 agent 就继续完成无用任务。

组报告准确声明、假设、依赖版本、编译/公理/语义状态及一个明确请求。总协调看压缩的数学接口和实际进度，不收集每个 worker 的全量日志。汇报区分已登记、实际执行、等待、交付和已验收。

## 6. 什么情况下根本不需要多 agent

短文档编辑、几处路径/命名修改、低级脚本已能解决的错误，由当前执行者或脚本完成。只有可独立交付的工作收益超过准备上下文、协调和集成成本时才分派。这是任务成本判断，不是给项目设置人数上限。

L0.3 可以按实际商/IsColimit、源覆盖范畴与 fiber 比较、独立原文范围审查等形成多个问题包；如果它们各自又有大量独立的就绪节点，可以继续扩大组内并行。若都要修改同一个 CoverAction，则先由接口 owner 处理冲突，不复制多套 CoverAction/card。

## 7. 方法约定与工具现状分开

以上采用 SHEAF 的 coordinator/maintainer/lead/worker 分工、队列认领、组内续领、共享库落位和快照构建方法。原型参考：[lead](https://github.com/frenzymath/SHEAF/blob/6e5abd804e1b0c8d4626349e3508103c97452711/template/roles/lead.md)、[maintainer](https://github.com/frenzymath/SHEAF/blob/6e5abd804e1b0c8d4626349e3508103c97452711/template/roles/maintainer.md)、[tools](https://github.com/frenzymath/SHEAF/blob/6e5abd804e1b0c8d4626349e3508103c97452711/template/tools/README.md)。

本轮只修改方法论；未安装这些上游并发执行脚本、Windows 快照发布器或自动数学任务调度。现有 lean_queue 是低级任务队列，不能冒充完整 SHEAF DAG 认领服务。实际启动大规模证明前须落实相应原子认领/隔离/落位机制；这些工程需求不构成预设 agent 人数上限，也不要求此次文档编辑去实施整个调度平台。

## Subagent 与 durable teammate 的分工（2026-10-22 用户确认）

- **stage 1 可以大量派给 subagent**：范围核对、consumer 定位、文件/声明盘点、精确缺口、写 stage1 记录。输出必须是带路径、SHA、对象/量词、consumer 和下一 statement 的完整记录。
- **stage 2/3 默认交给 durable teammate**：需要跨轮记忆、文件所有权、接口演化、依赖更新和反复编译反馈；subagent 上下文短，不适合承担长期证明主线。
- 可交给 subagent 的 stage 2/3 例外：单个文件、单一精确声明、已有完整公共供体、无需跨轮记忆、可在一次 bounded 任务内编译验收。
- subagent 的 stage1 记录是 teammate 接手的唯一接口；teammate 不应要求 subagent 记忆历史。
- teammate 名额仍为 8；subagent 是 stage1 扩容和 bounded lemma 的补充，不是替代长期 owner。
