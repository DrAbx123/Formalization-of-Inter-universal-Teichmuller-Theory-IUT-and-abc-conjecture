## 1. 先登记全树，再开放任务

每一轮执行前，先登记全部已知角色、唯一上级、精确文件白名单、任务契约和依赖。校验通过后才允许读取项目文件、执行任务。发现需要扩展树时，暂停受影响分支，登记新节点与依赖，重新检查权属，再启动新增任务。

默认采用五级 agent。用户是总协调的唯一决策上级，不计入 agent 层数。

```text
用户
└─ L0 总协调 GPT
   ├─ L1 领域主管 GPT
   │  ├─ L2 模块主管 GPT
   │  │  ├─ L3 文件负责人 GPT 或 DeepSeek
   │  │  │  ├─ L4 原子任务工人 DeepSeek
   │  │  │  └─ L4 原子任务工人 DeepSeek
   │  │  └─ L3 另一文件负责人
   │  └─ L2 另一模块主管
   └─ L1 另一领域主管
```

这是角色模板，不表示已经给仓库文件或 API 建立了上述执行节点。可以在领域与模块之间增加子领域主管，但新增层级必须拥有实际裁决职责；不能仅把同一上下文逐层复述。初始建议每个主管直接管理 2–4 个子节点，随后依任务边界调整，不为凑人数制造任务。

| 层级 | 本层负责的决定 | 收到的材料 | 向唯一上级提交 |
| --- | --- | --- | --- |
| L0 总协调 | 总目标、权属冲突、资源预算、跨领域优先级 | 领域报告与结构化验证证据 | 本轮实际结果、阻塞与未解决边界 |
| L1 领域主管 | 领域数学范围、论文语义边界、跨模块依赖 | 模块契约、接口报告、来源说明 | 领域结论及其精确适用范围 |
| L2 模块主管 | 将目标拆成依赖图、确定先后、处理接口请求 | 文件负责人的目标与依赖报告 | 模块状态、已证前置条件、阻塞链 |
| L3 文件负责人 | 独占源码、确定局部命题、集成候选、请求编译 | 自己的白名单文件、工人候选、已证接口 | 冻结目标的验证证据、接口更新、失败事实 |
| L4 原子任务工人 | 一个已限定的小任务 | 必要的目标上下文和已证接口 | 候选证明、局部分析或精确缺口 |

GPT 优先承担数学边界判断和复杂文件维护；DeepSeek 优先承担目标固定的小证明候选、已提供报错的分析、有限步骤检查。是否分配给 DeepSeek 依据小规模实测，不预先假定它能完成所有这些任务。L3 如果由 DeepSeek 担任，也适用完全相同的所有权与验收规则。

## 2. 文件独占是所有权，不只是写锁

- 每个文件在本轮只有一个 agent owner；读取也受限制。暂停、超时、重试和结束任务都不会自动让另一个 agent 获得该文件。
- 白名单列出精确路径及 `read` / `append` / `write` 权限；默认每个执行 agent 只持有 1–3 个工作文件，另有必要的独占记录文件。主管和纯推理工人可以是空白名单。
- 父级不能打开子级文件来审查；禁止通过全仓搜索、补丁展示、复制工作树、转发全文或拼接大量片段绕过限制。已有源码正文不随上下文全量继承。
- 允许 owner 导出必要的接口契约：确切命题、显式假设、类型、已证状态、版本与用途。该消息不是读取其他文件的授权，也不得包含与任务无关的实现正文。
- 多个小任务涉及同一现有文件时，由同一个 L3 排队集成。L4 返回新候选内容；L4 不读取或写入 L3 的源文件。
- 需要实验文件的 L4 必须预先登记其独占的精确新文件路径。它不能因此读取父级文件。只做推理的 L4 无需文件权限。
- 新增文件必须先登记 owner。所有权在本轮固定；失败后优先恢复同一逻辑 agent，不另派 reviewer 或替补偷偷接管。跨轮交接需要明确的新协议，不能仅靠重命名 agent 绕过限制。
- 统一日志由指定记录者独占追加，其他 agent 以消息上报。若设置局部日志，同样只由其 owner 访问。公共项目规则由协调层注入消息，不要求所有 agent 重读同一规则文件。

文件网关应按 Windows 的实际文件身份校验路径，处理大小写、`..`、junction、符号链接、硬链接及路径前缀混淆。不能只检查字符串是否以 `D:\lean` 开头。

## 3. 下发任务前冻结数学契约

每个任务至少包含：

```text
run_id, agent_id, parent_id, role, provider, model
task_id, target_id, whitelist, baseline_version
exact_goal, explicit_assumptions, permitted_change_scope
proved_dependencies, dependency_versions, source_provenance
verification_policy, acceptance_criteria
request_budget, token_budget, deadline, retry_limit
```

`exact_goal` 包括完整量词、变量类型、局部上下文、前提与结论。新任务不能把未知结果登记成“已证接口”。若尚不能明确这些字段，就先完成目标澄清或底层证明，而不是启动依赖它的任务。

防止偷换目标的验收要求：

1. 候选只标记为 `CANDIDATE`，不算证明完成。
2. L3 将候选集成到冻结目标中；既有声明可将允许修改范围限定在证明体，目标签名与导入版本另外校验。
3. 受控验证检查目标契约一致性、实际编译结果、依赖与公理边界，并将结果绑定到被验证内容的版本或哈希。后续改动会使对应证据失效。
4. 新增假设、削弱结论、换对象后证明同名命题，均不得作为原任务完成；需要上报并重新讨论目标。不得用 `sorry`、新增假公理或未证明的接口字段支撑后续数学。
5. 编译通过只证明实际形式命题在其依赖下成立。论文忠实性、目标是否正确和既有依赖是否含缺口，仍须分别给出依据；不能由“编译成功”代替。

本轮读到的既有审计日志末尾记录了生产树的一个历史 `sorryAx` 边界；本轮没有重新验证该历史状态。后续任务必须核实自身依赖是否触及该缺口，不能因为其已存在便默认可用于新证明。

## 4. 跨边界反馈：先停，再逐级路由

agent 需要他人文件的信息、接口变更或数学前提时：

1. 保存当前事实、失败尝试及下一步，进入 `WAITING_FEEDBACK`；不继续依赖该请求的推理、修改或提交。
2. 只向自己的直接上级提交请求，包含 `request_id`、所需接口、阻塞原因、相关目标和要求的版本。
3. 直接上级能解决就回复；否则逐级送达两分支的最近共同祖先，再沿目标分支下发至 owner。不允许平级私下互改，也不建立第二个上级。
4. owner 通过原路径返回接口契约、已验证事实或“当前无法提供”的具体原因。
5. 发起者收到匹配请求、匹配版本的明确答复后，才恢复。超时仅触发升级或重排；沉默不视为答复，更不视为许可。

主管维护等待依赖图。若形成循环，最近共同主管先确定真正的基础依赖，拆小任务或重新安排顺序，再通知相关节点。不能靠互相假设待证命题消除循环。

一个处于等待状态的 agent 不私自切去别的任务；主管可以调度其他已登记、数学上独立且权限不冲突的节点。

## 5. 逻辑角色常驻，模型请求按需运行

逻辑 agent 是稳定的角色与状态，不等同于一个一直开着的模型请求。每次唤醒只加载本节点任务、必要接口、本节点的 checkpoint 和新消息。含源码的私有状态不能向其他节点传递。

```text
REGISTERED → READY → RUNNING
RUNNING → WAITING_FEEDBACK → READY
RUNNING → CANDIDATE → VERIFYING → DONE
VERIFYING → NEEDS_REVISION → READY
RUNNING / VERIFYING → BLOCKED 或 FAILED
```

- 调度器尽可能并行执行无依赖且权限不冲突的 `READY` 节点，同时设置全局、GPT 请求、DeepSeek 请求和编译任务各自的并发上限及速率预算。同一逻辑节点最多保留一个有效在途请求，防止状态竞争。
- 父级下发任务或进入等待后保存状态，结束本次请求，释放运行名额。子级结果到达时，再唤醒该父级。不能让全部运行名额被等待中的祖先占住。
- 即使只有一个工作请求名额，也可以按队列推进五级树；多出来的名额用于执行独立节点。文件所有权与逻辑身份不随轮换变化。
- 设置有限重试、请求预算和失败升级路径。优先解除关键依赖，同时用等待时长避免独立任务长期得不到执行。
- checkpoint 至少保存目标与依赖版本、白名单版本、当前状态、已尝试方法、验证结果、未完成请求和下一步。恢复时复核版本，不能凭压缩摘要扩大已有结论。
- 换模型或换 provider 不自动继承文件权限。对已读源码的 owner，本轮不默认做跨模型接管；空白名单任务可以重新分配，但需结束旧任务并清楚登记新任务关系。

本轮内置审查团队可同时使用的 agent 名额为四个（含根节点），因此本轮并未运行一棵同时常驻的五级执行树。未来 API 调度器的逻辑节点数与同时在途请求数应分别管理。

## 6. DeepSeek 接入边界

DeepSeek 工人通过 provider adapter 接入同一套任务协议：`提交任务 → 返回结构化候选 → 校验结果 → 交给直接上级`。模型名称、API 地址、认证方式和限额在实际接入时核对，本文不假定当前接口参数或价格。

- 使用独立任务上下文，不向 DeepSeek 自动转发整段 GPT 对话、仓库目录或上级私有源码。
- 工人只收到其权限内、完成该任务所需的内容。无文件工人只接收导出的目标与接口。
- API 密钥由运行环境的凭据配置提供，不写入仓库、agent 提示词或研究日志；日志可记录请求编号、模型标识、耗时、用量和错误类别。
- 第一步先接入纯文本小任务。新增工具能力必须经过同一权限网关；模型不能直接获得任意 shell、文件系统或网络工具。
- 请求失败、限流、超时或输出格式错误时有限重试，随后报告上级；不得让模型通过扩大读取范围自行补上下文。
- 每次调用绑定任务版本、请求编号、尝试编号、目标及输入指纹。结果提交去重，过期目标或已取消请求的迟到结果只保留为历史，不自动写入当前文件。本地只落地一次不等于远端只执行或计费一次；超时重试也要计入预算。

本轮未查找或使用 API 凭据，未发送任何 DeepSeek 请求，也没有验证其连通性、费用或证明表现。

## 7. 权限执行与编译服务

只在提示词里写白名单属于行为约束，不是技术隔离。实际系统需要统一网关拒绝越权的读取、搜索、写入和工具调用；再用受限工作进程等手段防止绕过网关。当前原生审查 agent 共享工作环境，本轮依靠空白名单和不使用文件工具遵守约定，不宣称已经具备操作系统级隔离。

有一个必须明确的边界：Lean / Lake 编译会隐式读取导入依赖、配置和编译产物。设计建议让独立、无模型的受控构建服务读取被固定版本的依赖并验证；这些内容不交给调用 agent 阅读。构建日志中的源码片段只返回对应 owner，上级仅接收结构化证据。

这依赖于将“agent 阅读文件”与“受控编译器读取依赖”区分开。若文件独占要求也覆盖编译器的所有传递读取，就必须先重做构建权限设计；不能默默把编译依赖设为所有 agent 的公共白名单。该边界在实际源码执行前明确，当前文档阶段无需编译。

构建服务应使用固定版本的输入与隔离产物目录，防止其他 owner 正在写文件时混入不同版本。它只能执行被登记的验证步骤，不拥有修改数学源码的权限。

Lean 元程序、`#eval`、trace 和定义展开也可能访问或输出其他文件的内容。固定命令加普通报错过滤不足以形成隔离，还需要限制构建进程的输入、文件权限与输出通道；这些控制属于待实现内容。

## 8. 本轮角色与后续实现顺序

本轮只运行架构审查，实际角色为：

```text
/root
└─ /root/architecture_supervisor
   ├─ /root/architecture_supervisor/ownership_protocol
   └─ /root/architecture_supervisor/hybrid_scheduler
```

三名审查 agent 的文件白名单为空，只向直接上级报告。根节点独占以下四个路径：

| 文件 | 权限与用途 |
| --- | --- |
| `D:\lean\agents.md` | 读取规则；用户追加持久化要求后，根节点获分配追加启动与恢复协议 |
| `D:\lean\心得.md` | 已只读用户反思，保持原文 |
| `D:\lean\AUDIT_LEDGER.md` | 读取相关末尾、追加本轮事实 |
| `D:\lean\MULTI_AGENT_ARCHITECTURE.md` | 创建及维护本方案 |

后续实现依次为：

1. 实现节点登记、路径独占校验、消息与状态持久化，先用离线模拟任务验证五级树的路由与恢复。
2. 实现文件网关和受控验证边界，检查越权读取、上级复读、循环等待、陈旧结果及重复提交都会被拦截。
3. 接入一个 GPT 协调节点和少量 DeepSeek 无文件工人，测量实际质量、调用成本及等待时间。
4. 为一个确切的 Lean 底层子目标登记全部角色与文件 owner，从小范围开始；目标及依赖未固定前不铺开项目任务。
5. 在验证协议可用后增加独立分支与逻辑节点数，根据资源逐步提高实际并发。

这些是待实施步骤；本轮交付不把架构文档算作数学证明进展或已运行的软件系统。

## 9. 跨上下文持久化：不依赖模型记忆

协议标识：`iut-agent-tree/2026-10-13-v1`。

持久信息分为三种，职责不能混用：

| 载体 | 保存内容 | 当前状态 |
| --- | --- | --- |
| `agents.md` | 启动、恢复、独占与反馈的必要规则；新上下文的项目规则入口 | 本轮追加 |
| 本文 | 分层架构、角色职责、工具边界和实现方案 | 已写入；是方案，不是运行状态 |
| `AUDIT_LEDGER.md` | 追加的角色登记、权属调整、决定、检查事实与未完成事项 | 现有日志，本轮追加记录 |

后续实现调度器时，另设机器可校验的节点/权属注册表与 owner 私有 checkpoint。它们是待实现部件，不能把目前的 Markdown 日志假装成能自动恢复或拒绝越权的执行器。

启动与恢复遵循以下顺序：

1. 新会话、上下文压缩、进程重启、模型更换或任务续跑后，默认 `NOT_READY`。旧消息中的“我记得”或自然语言摘要不提供执行权限。
2. 根节点在固定启动白名单内读取项目规则及相关最新记录，确认协议版本和当前是否仅处于设计阶段。非根节点不自行读取公共文件，而由唯一父级提供规则包及本节点的状态包。
3. 恢复稳定的逻辑身份、唯一父级、精确白名单、任务与目标版本、已证依赖版本、检查点、预算及未回复请求。缺少字段或记录冲突时，先请求父级解决，不能重新扫仓库自行补齐。
4. 重建等待关系，核对上次有效证据。此前 `WAITING_FEEDBACK` 的节点在收到匹配回复前仍然等待；过期候选仍然不能落地。
5. 子节点回报状态摘要，由父级核对持久登记后发送明确的 `RESUME`。所需登记和校验完成后才转为 `READY`；原先等待反馈的节点仍需满足原请求的解锁条件。根节点依据已记录的授权及状态恢复，并追加恢复决定；子节点经父链报告，不共同读写这份日志。

调度器还需保存执行实例代次、最后已处理事件编号、在途请求及未决预算。恢复前撤销旧实例权限或确认其停止，确保同一逻辑节点最多一个有效执行实例；旧实例的迟到操作不能继续落地。权限变更先持久提交再生效，检查点完整写入后才切换当前版本。崩溃时无法确认的操作标记为 `UNKNOWN`，由原 owner 或受控服务核实，不推断已成功或已失败；不因恢复而清空尚可能计费的 API 请求账目。

每次请求由调度器重新注入规则版本和本节点权限包，不只依赖会话首条提示。新子任务不继承含其他 owner 源码的完整上下文；应使用独立上下文和最小任务包。

真正的执行约束必须位于模型之外：网关在每次工具调用及结果落地时检查角色、父级、协议与任务版本、路径 owner、操作权限及当前状态；未登记或非就绪请求默认拒绝。agent 自称“规则已更新”不能修改权限；权限只能经协调登记流程更新。受控构建使用单独受限的能力，不能让模型借它执行任意文件读取。
